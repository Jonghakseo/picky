# Picky UX Writing Guide

Picky · 제품 문구 · 한국어·영어

---

사용자가 지금 알고 싶은 것과 다음에 할 수 있는 행동을 먼저 쓴다. 짧게 쓰되, 판단에 필요한 조건과 결과는 빼지 않는다.

이 문서는 Picky 제품 문구의 기준이다. 시각 설계는 [디자인 원칙](./PRINCIPLES.md), 번역 구현은 [i18n 가이드](../docs/i18n.md)를 따른다. 아래 예시는 표현의 기준이며, 적용할 때는 현재 코드의 동작을 다시 확인한다.

## 문구를 쓰기 전에

다음 네 질문에 답한다. 답이 없으면 문장을 다듬기 전에 화면과 동작을 확인한다.

1. 사용자는 무엇을 하려는가?
2. 지금 상태는 무엇이며, 누가 무엇을 기다리는가?
3. 이 버튼을 누르면 무엇이 바뀌는가? 어느 대화·작업에 적용되는가?
4. 전송, 삭제, 중단, 비용, 복원에 관해 알아야 할 조건이 있는가?

View의 문자열만 보지 않는다. 액션, 상태 projection, 설정 저장, 로컬 에이전트의 수락·거부 조건까지 필요한 범위를 추적한다. 문구와 기능이 다르면 문구로 결함을 가리지 않는다.

## 문체와 정보량

- 한국어 설명은 해요체로 쓴다. 버튼·제목·상태는 짧은 명사나 행동 표현을 쓴다. `입력 대기`, `대기 요청 삭제`, `계정 연결`처럼 대상과 뜻을 드러낸다.
- 영어는 직접적이고 간결하게 쓴다. 인접한 같은 종류의 컴포넌트와 대소문자 스타일을 맞춘다. 브랜드·API·명령 이름의 표기는 보존한다.
- 오류에는 농담, 감탄, 책임 전가를 넣지 않는다. 실패한 일과 가능한 다음 행동을 말한다.
- 제목과 설명이 같은 말을 반복하면 설명을 뺀다. 레이블만으로 알 수 없는 범위·예외·적용 시점이 있을 때 설명을 더한다.
- 버튼에 모든 설명을 넣지 않는다. 버튼은 행동, 옆 설명은 조건과 결과를 맡는다. 중요한 삭제·전송 경고를 hover 도움말에만 숨기지 않는다.
- 한 설명에 목적이 여러 개면 나눈다. 글자 수 제한에 맞추려고 조건을 삭제하거나 글자를 작게 만들지 않는다.
- `중립적 데스크톱 컨텍스트`, `SwiftUI 작성기`, `auth storage`처럼 구현을 설명하는 말은 일반 사용 화면에서 빼거나 풀어 쓴다. 개발자 설정의 정확한 경로·프로토콜·도구 이름까지 지우지는 않는다.
- 사용자를 안심시키려고 `항상`, `절대`, `안전한`, `필요 없어요`를 덧붙이지 않는다. 코드와 서비스 조건이 보장하는 범위만 말한다.

## 용어 기준

같은 개념을 화면마다 바꿔 부르지 않는다. 아래 표는 일반 UI의 기본값이지 코드 식별자나 외부 콘텐츠를 치환하는 사전이 아니다.

| 개념 | 한국어 기본 표현 | 영어 기본 표현 | 구분할 것 |
|---|---|---|---|
| 제품·독립 작업 이름 | Picky, Pickle | Picky, Pickle | 제품 이름은 유지한다. Pickle의 역할은 처음 필요한 곳에서 설명한다. |
| 대화 기록 | 대화 | Conversation | 내부 session ID·세션 파일을 다루는 고급 정보에는 세션을 쓸 수 있다. |
| 수행하는 일 | 작업 | Task | 대화 전체와 현재 작업을 구분한다. |
| 요청·응답 묶음 | 요청과 응답, 이전 요청 | Request and response, earlier turns | 전체 대화와 같은 이름으로 부르지 않는다. |
| 작업 표시줄 | 도크 | Dock | 한국어에서 독·Dock·도크를 섞지 않는다. |
| 빠른 텍스트 입력 | 빠른 입력 | Quick Input | 퀵 인풋·퀵 입력을 섞지 않는다. |
| 음성 단축키 | 눌러서 말하기 | Push to Talk | 사용자 설정 화면에는 PTT만 단독으로 쓰지 않는다. |
| 실행 중 지시 | 작업 중 전달, 지시 보내기 | During current work, send guidance | 즉시 응답하거나 현재 도구를 중단한다고 약속하지 않는다. |
| 후속 요청 | 후속 요청, 응답 후 전달 | Follow-up, after current response | 대기열에 추가하는 일을 시간 예약과 혼동하지 않는다. |
| 입력 라우팅 | 입력 대상, 입력 대상 배지 | Input target, input-target badge | 카드를 여는 행동과 입력 대상을 지정하는 행동은 다르다. |
| 화면 정보 | 화면 정보, 화면 첨부 | Screen context, screenshot attachment | 모델의 컨텍스트 사용량과 구분한다. |
| 숨기고 유지 | 보관 | Archive | 중지·닫기·영구 삭제와 구분한다. |
| 저장된 파일 | 결과물 | Artifacts | 결과물의 종류나 저장 조건이 중요하면 보충한다. |
| 실행 이력 | 도구 기록 | Tool history | 툴·도구를 섞지 않는다. |
| 터미널 화면 | 터미널, Pi 터미널 | Terminal, Pi terminal | 일반 탭 이름에 TUI·SwiftUI를 노출하지 않는다. |
| AI 서비스 로그인 | 계정 연결 | Connected accounts | OAuth는 필요한 고급 설명에 남긴다. |
| 예약 서비스 설정 | 예약 자동 실행 설정 | Set up background scheduling | 서비스 설정과 새 예약 만들기를 구분한다. Cron 이름은 식별이 필요한 곳에 남긴다. |

새 용어가 필요하면 기존 화면과 카탈로그를 먼저 찾는다. 브랜드를 없애거나 기술 용어를 일괄 치환하는 식으로 통일하지 않는다.

## 상태와 행동을 구분하기

| 상황 | 쓸 표현 | 피할 오해 |
|---|---|---|
| 작업이 실행됨 | 실행 중 / Running | 단순 연결 상태를 실행 중으로 표시하지 않는다. |
| 실행 순서를 기다림 | 대기 중 / Queued | 사용자의 답변을 기다리는 입력 대기와 구분한다. |
| 사용자 답변이 필요함 | 입력 대기 / Waiting for input | 질문 폼의 답변과 입력창의 추가 지시를 구분한다. |
| 요청 처리가 실패함 | 실패 / Failed + 가능한 회복 행동 | 실패를 완료나 취소로 표현하지 않는다. |
| 현재 조건에서 진행할 수 없음 | 진행 불가 / Unable to continue | 단순 대기와 구분한다. |
| 아직 전달되지 않은 요청을 다시 보냄 | 다시 시도 / Retry | 이미 수행한 작업을 계속하는 행동과 구분한다. |
| 수락된 요청의 다음 작업을 진행함 | 이어가기 / Continue | 원래 요청을 똑같이 재실행한다고 암시하지 않는다. |
| 대기 텍스트를 편집할 수 있게 돌려놓음 | 입력란으로 옮기기 / Move to input | 재전송이나 삭제만 하는 행동처럼 표시하지 않는다. |
| 플러그인 삭제 확인창을 엶 | 삭제 / Remove | 설치됨 같은 상태를 행동 버튼 이름으로 쓰지 않는다. |

하나의 상태가 전사 처리와 응답 대기를 모두 포함한다면 `요청을 처리하고 있어요`처럼 둘을 포함하는 표현을 쓴다. 특정 단계명을 보여주려면 먼저 그 단계를 구분할 상태 정보가 있는지 확인한다. 빈 목록을 로딩 중이라고 쓰거나 미분류 개수를 분류 실행 중이라고 쓰지 않는다.

## 컴포넌트별 문구

| 위치 | 담을 내용 | 예시·주의 |
|---|---|---|
| 버튼·메뉴 | 행동과 필요한 대상 | `대기 요청 삭제`. 누르면 관리 창이 열리는 경우 `picky 명령 관리`. |
| 설정 토글 | 켰을 때의 효과, 필요한 예외 | `자동 화면 전송 제한`. 직접 포함한 화면의 예외는 설명에 적는다. |
| 입력란 | 무엇을 입력하는지 | 질문 대기 중에는 질문 폼에서 답한다는 점과 별도 지시를 구분한다. 필수 안내를 placeholder에만 두지 않는다. |
| 빈 상태 | 무엇이 없고, 무엇을 할 수 있는지 | `선택한 기간에 기록된 사용량이 없어요.` 실제 기록이 생기는 조건을 알린다. |
| 오류 | 실패한 일, 확인된 원인, 가능한 다음 행동 | `첨부 파일을 업로드하지 못했어요. 파일을 확인한 뒤 다시 시도해 주세요.` 원인을 모르면 추측하지 않는다. |
| 확인창 | 대상, 변경 범위, 되돌릴 수 있는지 | `분류 결과만 삭제`처럼 초기화 범위를 한정하고, 자동 재분류 조건도 알린다. |
| 도움말·접근성 | 아이콘의 행동, 대상, 현재 상태 | `보고서 열기`, `%@ 열거나 닫기`. 색·아이콘 모양만 설명하지 않는다. |
| 통계 | 실제로 집계한 값 | Pickle 수를 집중도, 지시 횟수를 작업의 깊이로 부풀리지 않는다. |

다음 업데이트에 콘텐츠가 추가된다는 보장이나 원인 불명의 오류에 대한 해결 약속을 만들지 않는다. 단축키는 현재 설정값을 표시한다. 값을 표시할 수 없다면 `설정한 눌러서 말하기 단축키`라고 쓰고 기본값을 고정하지 않는다.

## 빠뜨리면 안 되는 조건

### 전송과 개인정보

- 로컬 실행·로컬 저장·외부 서비스 전송은 별개다. Picky 계정이 필요 없다는 사실을 AI 제공업체 로그인이나 요금도 없다는 뜻으로 넓히지 않는다.
- 화면 캡처와 모델 전송을 구분한다. 자동 전송 제한이 켜져 있어도 사용자가 직접 포함한 화면은 전송될 수 있다.
- 포함 예정인 화면에는 `다음 요청에 포함`처럼 시점을 쓴다. 아직 보내지 않았는데 전송 중으로 보이게 하지 않는다.
- 진단 첨부를 꺼도 직접 선택한 파일은 남을 수 있다. 진단·사용자 첨부를 구분한다.
- 로그의 민감정보 가림을 완전한 제외로 표현하지 않는다. 별도 대화 기록 파일을 보내지 않는 것과 로그에 텍스트가 남을 수 있는 것은 다르다.

### 중단·복원·삭제

- 닫기·보관·작업 중지·대기열 삭제·영구 삭제를 구분한다.
- 중단 후 텍스트는 복원되지만 화면 첨부는 복원되지 않는다면 두 결과를 함께 알린다.
- 일괄 삭제의 숫자와 설명은 실제 삭제 가능한 항목을 기준으로 한다. 남겨 두는 항목을 숨기지 않는다.
- 명령 전송 성공과 서버의 처리 완료는 다르다. 완료·성공 문구에는 그 결과를 확인할 근거가 있어야 한다. 실패한 작업을 성공한 것처럼 숨기는 optimistic 상태도 확인한다.
- 문구 검수 중 데이터 손실이나 거부 조건을 발견하면, 표현만 고치지 말고 필요한 상태 제한·실패 표시를 함께 다룬다. 큰 프로토콜 변경이 필요하면 미해결 범위와 후속 작업을 명시한다.

## 한국어·영어 구현

1. `Picky/Resources/Localizable.xcstrings`에서 기존 키를 먼저 찾는다. 같은 의미의 키는 재사용하되, 서로 다른 행동은 같은 짧은 단어라는 이유로 합치지 않는다.
2. 두 언어를 함께 작성한다. 직역보다 의미를 맞추되 조건·부정·대상·시점·복원 범위는 같아야 한다.
3. SwiftUI의 지역화 키와 이미 해석된 `String`을 구분한다. `Text("key")` 같은 키 기반 API와 `L10n.t(...)`의 사용 경계는 [i18n 가이드](../docs/i18n.md)를 따른다. 문자열 변수·NSAlert·NSMenu·NSOpenPanel·모델 상태·알림·접근성 문구도 확인한다.
4. `%@`, `%lld`, 인자 순서·위치 지정·개수를 유지한다. 새 format 문자열은 `%1$@`, `%2$lld`처럼 위치를 지정한다. 숫자의 이하·미만, 실제 합계·추가 후 합계도 확인한다.
5. 사용자·에이전트가 쓴 내용, 도구 결과, 명령어, 파일 경로, 프로토콜 식별자는 번역 대상으로 바꾸지 않는다. 표시용 문구를 상태 판별 키로 쓰지 않는다.
6. 화면 문구와 접근성 라벨을 함께 맞춘다. 변경 전 영어 리터럴을 고정한 테스트는 실제 표시 계약에 맞게 갱신한다.

## 검수와 검증

- 문구 검수 요청만 받았다면 읽기 전용으로 조사한다. 수정 요청이 있어야 반영한다.
- 전수조사는 번역 카탈로그와 코드에 직접 적힌 문구를 모두 포함한다. 현재 진입 가능한 화면인지, 공용·중복 컴포넌트와 상태별 분기를 빠뜨리지 않았는지 확인한다.
- 앱 전반을 바꾸는 작업은 적용 전에 독립 검토를 받는다. 병렬 challenger로 화면 영역을 나눠 사실관계·정보 누락·용어·의미 변화를 검증한다. 작은 라벨 수정까지 같은 규모의 절차를 요구하지 않는다.
- 개인정보·중단·삭제·복구 문구는 실제 효과를 대조한다. 상태나 액션 분기를 바꿨다면 production 경로의 결과를 기존 행동 테스트로 확인한다.
- `scripts/check-localizations.sh`는 번역 누락 검사다. 문구의 사실관계, 자리표시자 호환성, 레이아웃이 맞다는 증거로 사용하지 않는다.
- 정적인 문구 변경은 diff·번역 키·자리표시자를 확인한다. Swift 사용처를 바꿨다면 필요한 컴파일 검증을 추가한다. 화면 잘림이 위험하면 production render나 허가된 UI 검증으로 확인하고, 보지 않은 화면은 검증했다고 말하지 않는다.
- 문서만 바꿀 때는 링크와 내용만 검증한다. 제품 빌드·전체 테스트를 습관적으로 돌리지 않는다. 실행 중인 앱은 명시적 허가 없이 재시작하지 않는다.

변경표는 `화면/키 | Before | After | 이유·동작 근거`로 작성한다. 전체 표를 요청받으면 대표 사례만 제출하지 않는다. 최종 저장된 값으로 표를 만들고, 두 언어·신규 안내·기존 키로 연결한 하드코딩 문구를 포함한다. 외부 출력이나 독립 진단 UI처럼 제외한 범위가 있으면 밝힌다.
