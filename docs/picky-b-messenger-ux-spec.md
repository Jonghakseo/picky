# Picky B 메신저 목업 UX 명세

- 버전: 목업 B.02, 2026-09-13 (KST)
- 기준: [기획서 B 0.3](./picky-grok-bot-port-prd-b.md)과 사용자가 전달한 `picky-b01-feedback.md`의 8개 의견
- [클릭 목업](./prototypes/picky-b-messenger/index.html) · [예약 전송 파트](./prototypes/picky-b-messenger/schedule-message.html) · [PR 링크 대상](./prototypes/picky-b-messenger/pull-request.html)
- 범위: HTML 화면과 모의 상호작용. Picky 제품 코드·Pi·명령·실제 PR은 실행하지 않는다.

## 1. 목적과 이번 변경

Picky에게 일을 맡기고, 담당자에게 대화로 방향을 바꾸거나 중단을 지시하고, 결과를 확인한다.
사용자가 도구 운영자가 될 필요는 없다. 전송 방식·작업공간·권한 로그를 매번 해석하게 하지 않는다.

| 받은 의견 | B.02에 반영한 계약 |
| --- | --- |
| 작업공간과 시안 설명을 빼기 | 모든 화면에서 작업공간명·경로, 컴포저 아래 부연, 목업 설명을 제거 |
| 중단 버튼 없이 채팅으로 제어 | 중단 버튼과 확인 모달 제거. 채팅 지시와 봇의 짧은 응답으로 처리 |
| 도구는 기본 자동 실행, 필요하면 ask | 테스트 승인 양식 제거. 에이전트가 만든 짧은 질문·선택지만 대화에 렌더링 |
| 모든 메시지는 steer, 별도 예약 전송 | steer/follow-up 선택과 작업 뒤 대기열 제거. 보내기 옆 예약 전송 추가 |
| 민트 DM에 모카가 말하면 안 됨 | DM은 사용자와 상대 봇만 발화. 다른 봇의 메시지는 접힌 인계 사건으로 표시 |
| PR 정보 최소화 | 기본 결과는 짧은 문장, branch, PR 번호, 링크. 근거는 상세로 이동 |
| 결과 확인은 Pickle이 처리 | S06을 자동 확인 중 상태로 변경. 사용자 확인·재시도 버튼 없이 모의 조회 후 완료 |
| 중단 UI 불필요 | S07도 채팅으로 중단한 뒤의 짧은 대화만 표시 |

기존 메신저 HTML을 파일 분리를 위해 다시 만들지는 않는다. 새 예약 전송과 PR 링크 대상은
별도 HTML로 만들고 `parts.css`를 공유한다. 앞으로 추가할 화면도 파트별로 나눈다.

## 2. 디자인 기준

| 항목 | 기준 |
| --- | --- |
| 첫 시선 | 상대 봇, 대화, 지금 필요한 답 또는 결과 |
| 기본 레이아웃 | 연락처와 선택한 대화의 2열. 상세는 사용자가 열 때만 3열 |
| 제품 화면 | 불필요한 부연·작업공간·운영용 ID·모의 실행 안내를 상시 노출하지 않음 |
| 목업 경계 | 제품 창 바깥에 `오프라인 목업 · 실제 실행 없음`만 유지 |
| 액션과 상태 | Action Blue는 행동·선택, 상태는 문구와 의미색으로 구별 |
| 입력 | 한 가지 보내기. 나중에 보낼 때만 예약 전송을 명시적으로 선택 |
| 세부 근거 | 필요한 경우 상세에서 확인. 적게 보인다는 이유로 데이터까지 삭제하지 않음 |
| 네이티브 한계 | HTML은 macOS 글꼴·입력·재질·접근성의 최종 증거가 아님 |

Light/Dark와 여유 있는 밀도/촘촘한 밀도를 같은 내용으로 비교한다. 본문 14px/13px은 이 목업의
제안값이며 HUD의 canonical 토큰을 바꾸지 않는다. 4px 간격 체계, 중립 표면과 제한된 radius를
사용한다. HTML 아이콘은 실제 SF Symbols 구현이 아니다.

## 3. 정보 구조와 소유권

- Picky는 고정 CBO다. 루나(조사), 민트(구현), 모카(검토)는 기존 Pickle을 재사용한다.
- `예약 날짜 수정`은 그룹 대화다. 그룹을 열었다고 새 Pi 세션이나 workspace를 만들지 않는다.
- 각 Pickle의 고정 홈·하나의 지속 대화·작업공간 분리는 내부 계약으로 유지한다. UI에서 경로를
  감추는 것이 실행 대상을 없애거나 같은 저장소를 무조건 공유하라는 뜻은 아니다.
- DM에는 사용자와 상대 봇의 발화만 표시한다. 그룹에서는 실제 참여자가 직접 말할 수 있다.
- 다른 봇의 전달은 발신자·수신자·전달 사실을 표시하고 세부 본문은 기본 접는다.
- 일시적인 하위 실행은 부모 봇의 상세에 속한다. sidebar에 새 연락처를 추가하지 않는다.
- 선택한 대화와 작성 중인 초안은 대화별로 보존한다. 예약 메시지도 작성 시 수신자를 고정한다.

## 4. 공통 화면과 입력

### 4.1 메신저

왼쪽 목록은 이름과 역할로 찾는다. 이는 fixture 연락처 필터이며 제품의 전체 검색 구현이 아니다.
대화 header에는 상대, 역할·상태, 상세 진입만 둔다. 중단 버튼은 없다.

composer는 입력창, 보내기, 예약 전송 버튼으로 구성한다. 하단 설명, 작업공간, 전송 mode,
예시 문장 채우기 버튼은 없다. 입력창 placeholder는 수신자만 알려준다.

- Enter는 항상 일반 메시지 전송이다. 실행 중이면 steer, idle이면 같은 지속 대화의 다음 turn이다.
- Option+Enter에도 follow-up 의미를 부여하지 않는다. Shift+Enter는 줄바꿈이다.
- IME 조합 중 Enter는 전송하지 않는다. 실제 NSTextView/한글 입력기는 별도 검증해야 한다.
- 질문의 선택 버튼은 일반 메시지와 다르다. 원 질문의 응답 ID로 처리한다.
- 중단은 `이 작업 중단해줘`, `그만해`, `멈춰줘` 같은 채팅 지시로 한다.

실제 제품에서는 Pi가 중단 의도·대상을 판단하고 내부 abort와 하위 실행 정리를 요청한다.
HTML은 몇 가지 정해진 문장만 분기하는 모의 동작이다. 이 키워드 분기를 Swift나 agentd의
의도 해석기로 가져오지 않는다. 장기 도구 실행 중 지시 수신과 중단 지연은 B §13.4의 별도 실험이다.

### 4.2 리뷰 도구

밝기·밀도·장면 선택·처음부터·피드백은 제품 창 바깥에 둔다. 장면 이동은 검토용 fixture를
새로 구성하며 대화 초안과 모의 예약을 초기화한다. 피드백은 보존한다.

`#screen=S04&view=mint&theme=dark&density=compact&panel=files`처럼 화면·대화·시각 변형을
지정할 수 있다. hash는 완전한 대화 저장 파일이 아니다. 새로고침하면 선택 장면의 기본 fixture로
돌아가므로 사용자가 입력한 대화·질문 응답·예약의 제품 영속성을 증명하지 않는다.

## 5. 화면별 UX

| 화면 | 첫 화면과 사용자 목표 | 사용자 행동 | 다음 상태 |
| --- | --- | --- | --- |
| S01 의뢰 | Picky와 짧은 인사, 작성할 메시지 | 의뢰 보내기 또는 예약 전송 | S02 팀 배정 또는 예약 보관 |
| S02 팀 배정 | 담당자와 역할만 있는 작은 팀 카드 | 그룹이나 담당자 대화 열기 | 같은 요청의 S03 |
| S03 실행 중 | 담당자의 짧은 진행 메시지 | 수정 지시, 대화로 중단, 메시지 예약 | S04 질문, S07 중단 또는 예정 시각까지 보관 |
| S04 선택 질문 | 에이전트가 만든 질문과 선택지 | PR로 공유 / 수정안만 남기기 | S05 결과 |
| S05 결과 | 짧은 완료 문장과 최소 PR 카드 | PR 링크, 접힌 인계, 필요한 상세 | 기존 대화를 유지하며 근거 열람 |
| S06 자동 확인 | 담당자가 결과를 확인 중이라는 짧은 메시지 | 별도 확인 작업을 요구하지 않음 | 모의 종료 기록 조회 후 S05 |
| S07 대화로 중단 | 사용자의 중단 지시와 봇의 짧은 답 | 새 메시지로 다음 의뢰 가능 | 같은 지속 대화에서 S03 |

### S01 · 의뢰

초기 composer에는 다음 문장을 넣어 흐름을 시작할 수 있게 한다. 시안 설명 문장은 별도로 넣지 않는다.

> 예약 화면에서 날짜를 바꾸면 인원이 초기화돼. 원인을 조사하고 수정한 뒤 별도로 검토해줘. 배포는 하지 마.

사용자가 편집한 입력은 그대로 표시한다. 봇 답변은 정해진 시나리오이며 임의 의뢰를 실제로
이해하지 않는다. 모델·계정 연결과 파일 작업 허용이 준비된 상황을 가정한다.

### S02 · 팀 배정

Picky는 루나 조사, 민트 수정, 모카 검토를 짧게 안내한다. 팀 카드에는 담당자·역할·대화 진입만 둔다.
실행 ID·worktree·workspace·새 세션 생성 내역을 나열하지 않는다. 그룹 진입은 다음 모의 진행 장면을
보여주는 장치이지 실제 작업 실행 버튼이 아니다.

### S03 · 실행 중

그룹에는 실제 참여자의 진행 메시지를 표시한다. 민트 DM에서는 민트만 답하고 루나의 전달은
`루나가 민트에게 메시지를 보냈어요`라는 접힌 사건으로 보인다. 같은 규칙을 모든 인계에 적용한다.

일반 입력은 모두 현재 작업에 전달한다. 예약하지 않은 입력을 다음 작업 대기열로 밀지 않는다.
이 목업에서 첫 수정 지시 뒤 S04 질문으로 이동하는 것은 고정된 시나리오다. 실제 제품이 모든
수정 지시마다 질문해야 한다는 뜻이 아니다.

### S04 · 에이전트의 선택 질문

도구와 테스트는 기본 자동 실행한다. 명령·cwd·branch·위험 설명을 한꺼번에 쌓은 승인 양식은 없다.
이 장면은 이미 수정·검토한 내용을 PR로 공유할지 사용자의 선택이 필요한 상황이다.

> 수정과 테스트를 마쳤어요. PR로 공유할까요?

선택지는 `PR로 공유`, `수정안만 남기기`다. 두 번째 선택도 테스트를 거절하거나 실패했다는 뜻이
아니다. PR 생성 여부만 달라진다. 일반 채팅을 버튼 선택으로 자동 해석하지 않는다.

실제 제품의 기본 자동 실행은 권한 검사 제거가 아니다. 계정 권한·TCC·사용자 금지·자원 소유권을
유지하고, 추가 판단이 필요하면 에이전트가 ask를 호출한다. 필요한 정보를 짧게 보여주되 실제
질문·응답·행동의 귀속을 잃어서는 안 된다.

### S05 · 결과

기본 PR 카드는 `#128`, `fix/date-change`, `PR 보기` 링크만 보여준다. 테스트 개수, 파일 개수,
실행 command, 관찰 revision, workspace는 기본 대화에 나열하지 않는다. 자세한 근거는 상세에서 본다.

PR 링크는 [별도 로컬 PR 파트](./prototypes/picky-b-messenger/pull-request.html)를 연다. 실제
GitHub에 PR을 만들거나 존재하지 않는 GitHub URL을 실제 결과처럼 제공하지 않는다. 별도 화면에도
제품 화면 바깥의 목업 표시를 둔다.

민트 DM에서 모카의 검토는 접힌 인계다. 모카를 민트 DM의 참여자처럼 렌더링하지 않는다.
Picky DM은 Picky가 결과를 전달한다. 현재 선택한 대화를 강제로 다른 DM으로 바꾸지 않는다.

### S06 · 자동 확인

사용자에게 ‘확인 필요’를 해결하라는 카드나 재시도 버튼을 주지 않는다. 담당자가 읽기 전용으로
저장된 종료 기록을 대조한다. 목업에서는 5초 뒤 확인된 종료 기록이 있는 장면으로 전환한다.
중단·다른 장면 이동 이후 오래된 모의 확인이 결과를 덮어쓰지 않아야 한다.

이는 실제 복구 구현이 아니다. 제품에서는 모르는 결과를 성공으로 바꾸거나 외부 효과를 확인 없이
다시 실행하면 안 된다. 스스로 해결하지 못하고 사용자의 답이 필요할 때만 ask로 묻는다.

### S07 · 대화로 중단

중단 지시와 `진행 중인 작업을 중단했어요`라는 짧은 답만 보여준다. 중단 버튼·중단 확인 모달은 없다.
이미 완료한 파일 변경·외부 효과를 되돌렸다는 뜻은 아니다. 작업 시작 전 중단했다면 가짜 diff도 없다.

중단은 해당 작업과 하위 실행에 적용한다. 독립적인 예약 메시지는 자동 삭제하지 않는다. 예약 삭제는
예약 목록에서 별도로 수행한다. 중단 뒤 새 의뢰도 같은 봇·같은 지속 대화에서 이어진다.

## 6. 예약 전송 파트

보내기 오른쪽 버튼으로 [예약 설정 HTML](./prototypes/picky-b-messenger/schedule-message.html)을 연다.
메시지와 수신자는 부모 화면이 열 때 고정한다. iframe에서 임의 수신자나 본문을 지정하지 않는다.

- n분 뒤: 직접 분 입력과 5분·30분·1시간 선택을 제공한다.
- 특정 시점: 날짜·시각과 시간대를 표시한다. 과거 또는 잘못된 시간을 거부한다.
- 예약 중에는 Pi에 전달하지 않는다. 예약 목록에서 시각 변경·삭제가 가능하다.
- 실제 시각에 도달하면 저장된 수신자에게 한 번 전달한다. 현재 보고 있는 DM으로 바뀌지 않는다.
- 전달 의미는 일반 메시지와 같은 steer다. ‘현재 작업이 끝나면’이라는 follow-up 조건이 아니다.
- 예약 편집 중 원 예약이 이미 발송되거나 삭제되었다면 새 예약으로 부활시키지 않는다.
- child 메시지는 해당 iframe, 현재 편집 token, 원 상태를 확인한다. 지난 dialog나 다른 frame의 입력을 무시한다.
- 다시 열 때 이전 폼을 먼저 숨기고, 새 수신자·본문·편집 token의 초기화 응답을 받은 뒤 표시한다. 이전 예약의 폼이 새 요청으로 제출되지 않게 한다.

목업은 탭이 열려 있을 때 브라우저 시간으로 동작하며 앱 영속 저장소나 OS 스케줄러를 쓰지 않는다.
새로고침·장면 초기화·탭 닫기 뒤 예약은 유지되지 않는다. 실제 제품의 영속성·재시작·DST·missed-run은
B §9.2.1의 구현·검증 대상이며 이 목업으로 입증하지 않는다.

## 7. 상세와 키보드

상세는 진행·변경 파일·검증 기록을 읽기 전용으로 연다. 상세를 본다고 작업이 멈추지 않는다.
원 요청·관찰 정보는 내부에 유지하고 사용자가 필요한 근거를 선택해서 본다.

모든 활성 버튼에 이름과 키보드 경로를 둔다. 상세 탭은 좌우 화살표, dialog는 Escape로 닫고
원래 제어로 focus를 돌려준다. native VoiceOver·TCC·PTT·NSTextView의 동작은 별도 제품 검증 대상이다.
일반 버튼은 arrow cursor와 hover를 사용한다. Reduce Motion에서 의미가 유지되도록 장식적 motion은 없다.

## 8. 피드백

제품 창 바깥의 `이 화면 피드백`에서 화면 ID·대화·상태·밝기·밀도·상세 상태와 의견을 기록한다.
브라우저 localStorage만 사용하고 자동 전송하지 않는다. 저장 불가 시 메모리에 보관하고 내려받기를
안내한다. 작성 중 다른 장면으로 이동해도 의견의 원 화면 귀속은 유지한다.

이전 B.01 의견은 같은 브라우저에 남아 있으면 보존한다. 새 내려받기 파일명은 `picky-b02-feedback.md`다.
공유하려면 내려받은 Markdown을 대화에 전달한다. 사용자가 제공한 원본 피드백 파일은 수정하지 않는다.

## 9. 확인할 사용자 계약

- 의뢰 → 팀 배정 → 그룹 → 수정 → ask → 결과 흐름이 이어진다.
- 작업공간·컴포저 부연·전송 mode·중단 버튼이 모든 장면에서 제거돼 있다.
- 일반 Enter와 Option+Enter는 steer이며, Shift+Enter·IME 조합은 전송하지 않는다.
- 중단은 채팅으로 처리하고, 부정 문장 `중단하지 마`를 중단 명령으로 처리하지 않는다.
- 테스트 결과는 도구 승인 없이 생기고, ask의 선택은 PR 생성 여부만 바꾼다.
- 민트 DM에는 모카·Picky의 발화가 없고, 인계는 기본 접혀 있다.
- PR 카드가 최소 정보만 보이며 별도 로컬 페이지로 연결된다.
- 예약은 조기·중복 전달하지 않고 원 대화로 보내며 시각 변경·삭제가 가능하다.
- 자동 확인은 중단·장면 전환 후 오래된 결과를 적용하지 않는다.
- 피드백 저장·복원·내려받기와 light/dark·밀도·좁은 화면이 동작한다.

## 10. 검증 방법과 한계

[브라우저 검증 스크립트](./prototypes/picky-b-messenger/verify-browser.js)는 실제 HTML과 예약 iframe을
별도 임시 프로필의 headless Chrome에서 조작한다. 기존 `playwright-cli`에 포함된 `playwright-core`와
설치된 Chrome을 재사용하며 새 의존성이나 실행 중인 사용자 profile을 요구하지 않는다.

```bash
node docs/prototypes/picky-b-messenger/verify-browser.js
```

2026-09-13 검증에서 `file://`로 메신저와 두 HTML 파트를 열어 10개 검증 묶음을 통과했다.
브라우저 오류와 외부 요청은 0건이었다. Light/Dark·좁은 화면·예약 창 스크린샷과 내려받은 피드백도 확인했다.
재오픈한 예약 폼이 이전 token으로 제출되는 오류를 재현한 뒤 초기화 완료 응답으로 고쳤다.

이 검증은 모의 화면과 메시지 전달만 증명한다. 실제 Pi 실행·기본 자동 도구 권한·ask enforcement·
장기 도구 중 채팅 중단·예약 영속화·GitHub PR·OS 복구·macOS 접근성을 검증한 것이 아니다.
공식 브라우저/네이티브 UI 검증과 기능 구현은 따로 수행해야 한다.
