# Picky Task 내재화와 실행 라우팅 확정안

- 버전: 1.0
- 확정일: 2026-10-08 (KST)
- 상태: 제품 정책과 내재화 방향 확정. 구현은 시작하지 않았다.
- 범위: 메인 Picky의 요청 분류, Task 실행·제어·결과 전달, 동의에 따른 Pickle 위임.
- 코드 조사 기준: Picky `a4999ce3b`, Task npm `@ryan_nookpi/pi-extension-task@0.0.1`.

이 문서는 사용자와의 설계 검토에서 확정한 결정을 기록한다. 문서 작성은 제품 코드 변경, 앱 재실행, 배포, npm 패키지 삭제를 실행하는 요청이 아니다. 실제 구현은 아래 계약과 검증 기준을 따른다.

기존의 “중장기·비단순 작업은 반드시 Pickle에 자동 위임” 정책을 교체한다. [기획서 A](./picky-pickle-bot-mvp-prd.md)와 [기획서 B](./picky-grok-bot-port-prd-b.md)의 자동 Pickle 생성·배정 설명도 이 문서의 적용 범위에서는 새 정책을 따른다. 기존 코드·주석·지침의 강제 위임 문구는 수정 대상이며, 새 정책을 막는 유지 조건이 아니다. 두 기획서의 메신저·봇·Routine 전체 개편을 이번 구현에 함께 포함하지 않는다.

## 1. 확정한 결정

| 항목 | 결정 |
| --- | --- |
| 즉답 | 번역·짧은 확인 등은 Picky가 직접 처리한다. 업무 도구 호출 1~2회 안에 바로 확인할 수 있는 요청이 대상이다. |
| 절차적 작업 | 파일 탐색·편집·열기, 여러 자료 검색·조사 등은 Task로 처리한다. |
| 무거운 작업 | 프로덕션 수준의 코드 작업처럼 유지보수·검증·Git 추적 등이 필요한 작업이다. Pickle 위임 여부를 먼저 묻는다. |
| 가벼운 작업 | 일상 작업과 일회성 스크립트 처리다. 코드나 셸을 쓴다는 이유만으로 무겁다고 분류하지 않는다. |
| 위임 질문에 동의 | Pickle을 생성해 위임한다. |
| 위임 질문에 거절 | 요청 자체를 취소하지 않고 Task로 진행한다. |
| 위임 질문 닫기 | 결정을 `pending`으로 보존한다. Task 실행이나 Pickle 생성으로 진행하지 않는다. |
| 명시적 Pickle 위임 요청 | 추가 확인 없이 새 Pickle을 생성해 위임한다. 기존 Pickle을 명시한 후속 지시는 해당 Pickle로 보낸다. |
| 구현 방식 | Task 원본 소스와 관련 테스트를 Picky로 이관해 전용 내장 모듈로 유지한다. 독립 npm 익스텐션과 이중 유지보수하지 않는다. |
| 초기 worker | 기존 RPC worker 구조를 유지한다. 내재화와 SDK worker 재작성을 동시에 하지 않는다. |
| 사용자 경험 | Picky가 Task 진행·질문·결과 전달을 맡는다. Task 때문에 독립 Pickle 대화를 만들거나 사용자를 다른 대화로 보내지 않는다. |

Task는 Picky 대화에 속하는 실행 단위다. Pickle은 사용자가 별도로 맡기기로 선택한 독립 대화다. Task가 오래 실행된다는 이유만으로 Pickle로 바꾸지 않는다.

## 2. 입력 대상과 요청 분류

### 2.1 입력 대상을 먼저 정한다

기존에 명시한 입력 대상을 보존한다. Pickle 대화에서 보낸 메시지, 고정·일회성 피클 입력 대상, 특정 Pickle의 후속 지시는 해당 경로를 유지한다. 메인 Picky의 새 분류 정책을 이유로 이를 가로채거나 새 Pickle을 만들지 않는다.

메인 Picky로 들어온 새 요청은 다음 순서로 판단한다.

1. 사용자가 Pickle 위임을 명시했으면 바로 생성·위임한다.
2. 프로덕션 수준의 코드 작업이면 위임 여부를 묻는다.
3. 여러 절차가 필요하면 Task로 처리한다.
4. 바로 답하거나 짧게 확인할 수 있으면 직접 처리한다.

자연어의 의도와 실행 방법은 Pi의 메인 모델이 판단한다. 앱에 키워드별 작업 분류기를 하드코딩하지 않는다. agentd는 승인 상태, 실행 대상, 작업 범위, 중복 실행 여부를 검사한다.

### 2.2 무거움은 소요시간보다 작업 성격으로 판단한다

| 요청 예시 | 기본 경로 | 판단 이유 |
| --- | --- | --- |
| 제공된 문장이나 화면의 짧은 번역 | 직접 | 이미 주어진 맥락으로 답할 수 있다. |
| 경로를 아는 파일 열기, 단일 사실 확인 | 직접 | 짧은 호출 1~2회로 끝난다. |
| 파일을 찾아 내용을 수정하고 열기 | Task | 탐색·수정·확인의 절차가 필요하다. 프로덕션 코드 변경이면 아래 규칙이 우선한다. |
| 여러 출처를 비교하는 주제 조사 | Task | 조사 절차가 필요하다. 오래 걸린다는 이유만으로 위임 질문을 추가하지 않는다. |
| CSV 변환·파일 정리용 일회성 스크립트 작성·실행 | Task | 코드 실행을 포함하지만 지속 유지보수할 제품 코드 작업은 아니다. |
| 프로덕트 버그 수정, 기능 구현, 유지보수용 리팩터링 | 위임 질문 | 수정량이 작아도 제품 코드의 검증·Git 추적·유지보수가 필요하다. |
| 프로덕션 프로젝트의 빌드·통합 검증 | 위임 질문 | 제품 코드 작업의 실행·검증에 해당한다. 이미 승인된 같은 작업의 검증이면 재질문하지 않는다. |
| “이 일은 피클에 맡겨줘” | 바로 Pickle | 사용자가 실행 대상을 선택했다. |

코드 조회·설명·조사를 했다는 사실만으로 프로덕션 코드 변경으로 분류하지 않는다. 일회성 스크립트를 나중에 제품 코드로 편입하거나 유지보수 대상으로 확대하면 달라진 범위를 기준으로 판단한다.

호출 횟수는 직접 처리 경로의 예상 업무량 기준이다. `bash` 한 번에 여러 절차나 긴 빌드를 넣어 우회하지 않는다. Task 생성·질문·상태 제어 호출과 실제 업무 도구 호출을 구분한다. 직접 처리하다 추가 절차가 필요해지면 이미 얻은 결과를 전달해 Task로 이어간다.

실행 경로 선택은 행동 권한을 확대하지 않는다. Task 선택이나 Pickle 위임 동의가 외부 발송·배포·삭제·비용 지출 등을 함께 승인하는 것은 아니다.

## 3. 위임 질문과 pending 계약

### 3.1 질문은 작업에 귀속된 결정이다

위임 질문은 `ask_user_question`의 기존 폼을 사용한다. 다만 일반 질문 결과와 달리, 원요청과 범위에 연결된 위임 결정을 별도로 저장한다. 모델이 `approved: true`라고 주장하는 것만으로 승인하지 않는다. 실제 사용자 응답이나 명시적 위임 요청과 연결돼야 한다.

| 사건 | 결정 상태와 실행 |
| --- | --- |
| 새 요청을 무거운 작업으로 분류 | 위임 결정을 `pending`으로 저장하고 질문한다. 아직 worker·Pickle을 시작하지 않는다. |
| Pickle 위임에 동의 | 해당 범위의 생성·위임을 한 번 실행한다. |
| Pickle 위임을 거절 | 해당 범위를 Task로 실행한다. 거절은 작업 취소가 아니다. |
| 질문 폼 닫기·답변 없이 종료 | `pending`을 유지한다. 기본값이나 모델 판단으로 진행하지 않는다. |
| 사용자가 작업 자체를 취소 | 결정을 종료하고 아직 시작하지 않은 실행을 막는다. 이미 실행한 부분이 있으면 정리 상태를 확인한다. |
| 같은 응답 재전송 | 이미 처리한 결정을 반환한다. worker·Pickle을 중복 생성하지 않는다. |
| 다른 범위로 바뀐 뒤 옛 답변 도착 | 옛 답변으로 새 범위를 실행하지 않는다. |

`pending`은 동시 실행 큐의 `queued`와 다르다. 사용자 결정 대기이며 실행 순서가 돌아와도 시작되지 않는다. 폼의 표시 수명과 결정의 수명도 다르다. 폼을 닫거나 연결이 끊겨도 결정은 남고, 다시 열어 답하거나 명시적으로 취소할 수 있어야 한다.

대기 중에도 Picky는 다른 요청을 받을 수 있다. 관련 없는 다음 메시지를 답변으로 소비하지 않는다. 음성·텍스트 답변은 어떤 질문에 대한 답인지 명확할 때만 연결하며, 모호하면 확인한다. 동시에 여러 결정이 있으면 하나씩 표시하더라도 모두 보존한다.

### 3.2 같은 범위에는 다시 묻지 않는다

사용자가 Task를 선택한 같은 목표·범위는 Task로 끝낸다. 내부에서 프로덕션 작업임을 다시 발견하거나 시간이 길어졌다는 이유로 위임 질문을 반복하지 않는다. 승인된 Pickle 작업도 정상적인 수정·빌드·검증 단계마다 재질문하지 않는다.

재판단은 사용자가 목표나 범위를 실질적으로 바꾼 경우에 한한다. 타임아웃·모델 실패·인증 실패를 자동 Pickle 전환의 근거로 사용하지 않는다. 실패와 가능한 회복 행동을 표시한다.

위임 동의 전에 피클용 worktree 생성 등 위임을 전제로 하는 준비 작업을 실행하지 않는다. 분류에 필요한 짧은 읽기 전용 확인은 가능하지만, 그 과정에서 본 작업을 시작하지 않는다.

## 4. 소스 내재화 방식

### 4.1 단일 유지보수 대상은 Picky다

`@ryan_nookpi/pi-extension-task@0.0.1`은 이관 원본이다. 배포된 TypeScript 소스와 README를 로컬 원본과 대조했고 일치함을 확인했다. 기존 구현을 참고해 처음부터 다시 쓰지 않고, 필요한 코드와 동작 테스트를 가져와 Picky의 계약으로 바꾼다.

최종 제품은 해당 npm 패키지 설치나 업데이트에 의존하지 않는다. 범용 host API를 먼저 공개하거나 독립 Pi 익스텐션 호환성을 유지할 필요도 없다. 이후 수정·검증·배포는 Picky 저장소와 제품 버전에서 관리한다.

| 원본 영역 | 이관 방향 |
| --- | --- |
| `manager.ts` | 큐·동시 실행 제한·revision·수정 지시·오래된 보고 차단을 보존한다. 저장·취소·호스트 이벤트 경계는 바꾼다. |
| `runtime/rpc-worker.ts` | Task별 별도 프로세스와 같은 세션에서의 수정·재개 구조를 유지한다. 번들 실행 경로와 환경을 명시한다. |
| `runtime/worker-bridge.ts`, `runtime/protocol.ts` | 명시적인 `task_report`, Task/revision 검증, 재귀 위임 차단을 유지한다. Picky 전용 질문·중단 경로를 연결한다. |
| `context/context.ts` | 참조 가능한 부모 대화 snapshot과 recall을 재사용한다. 원요청·첨부·실제 작업 폴더 전달을 보완한다. |
| `routing/*` | 실행 모델 tier 판단은 재사용할 수 있다. 설정·인증·허용 모델의 소유자는 Picky로 바꾼다. |
| `store.ts` | 부모 Pi 세션 ID별 독립 저장 대신 Picky 작업 저장 계층에 맞춘다. 이중 영속 상태를 만들지 않는다. |
| `index.ts` | 범용 익스텐션 진입점을 그대로 로드하지 않는다. Picky 내장 Task 도구와 호스트 연결로 교체한다. |
| 기존 테스트 | 큐·revision·보고·RPC 수명 등 보존할 계약의 테스트를 이관하고 바뀐 계약만 수정한다. |

원본의 설치된 Pi CLI 탐색 fallback, 사용자 전역 설정·프로젝트 `.pi/task.json` 자동 탐색, 사용자 확장 자동 발견은 Task 실행의 호환 경로로 남기지 않는다. 모든 SDK import는 저장소 규칙에 따라 `runtime/` 또는 `bootstrap.ts`에 둔다.

## 5. 실행 소유권과 저장

```text
사용자 입력
  -> 기존 입력 대상 결정
  -> 메인 Picky가 의도·작업 성격 판단
       -> 직접 응답
       -> 내장 Task -> RPC worker -> 보고·자원 정리 -> Picky 결과 전달
       -> 위임 결정 pending
            -> 동의: 기존 Pickle 생성·인계 경로
            -> 거절: 내장 Task
       -> 명시적 위임: 기존 Pickle 생성·인계 경로
```

Task를 숨겨진 Pickle이나 별도 도크 세션으로 구현하지 않는다. 별도 daemon도 만들지 않는다. Task worker는 Picky가 소유한 agentd에 귀속되고, Pi 프로세스는 실행 구현이다.

| 책임 | 소유자 |
| --- | --- |
| 요청 해석·경로 선택·작업 지시 | 메인 Pi 모델 |
| 메인 입력 세대·대화·질문 및 결과 조율 | `MainAgentCoordinator`와 그에 연결한 작업 서비스 |
| Task 스케줄링·revision·worker 제어 | Picky 내장 Task 실행 모듈 |
| 결정·작업 상태·완료 전달의 영속 정본 | Picky 작업 저장 계층 |
| worker 모델·도구·RPC 실행 | `runtime/`의 Task adapter |
| 상태 표시·사용자 제어 전달 | Swift 앱과 PWA |

기존 `AsyncTaskHostBridge`, 실행 상태·presence, 완료 ticket 계약을 재사용한다. 현재 Pickle 중심으로 연결된 host를 메인에도 연결한다. 새로운 Task 저장소와 원본 `tasks.json`을 둘 다 정본으로 쓰지 않는다. worker의 일시적인 실행 상태와 앱에 공개하는 영속 상태의 갱신 책임을 명확히 나눈다.

다음 식별 역할을 구분한다. 실제 필드명은 기존 프로토콜에 맞춰 정한다.

- 원요청과 사용자 입력 출처.
- Picky의 논리적 Task ID 및 지시 revision.
- 위임 결정과 해당 결정이 허용한 목표·범위.
- 표시 중인 질문 요청 ID. 다시 표시하는 폼이 옛 응답을 소비하지 않도록 한다.
- runtime instance·control generation 등 늦은 실행 이벤트를 거르는 식별자.
- 완료 전달 ID와 인계 대상 Pickle ID.

Task 소유권을 부모 Pi 세션 파일 ID에만 묶지 않는다. 메인 컴팩션·세션 교체·재시작 후에도 원래 작업과 결정에 접근할 수 있어야 한다.

## 6. 수명·중단·완료 계약

### 6.1 응답 종료와 작업 종료를 분리한다

Task 생성은 ID를 즉시 반환하고 Picky의 현재 응답을 끝낼 수 있다. 그 뒤에도 Task 상태를 확인하고 다른 요청을 보낼 수 있어야 한다. 부모나 worker의 일반 답변 종료, `agent_end`, `agent_settled`를 Task 완료로 판단하지 않는다.

성공 완료는 현재 revision의 유효한 `task_report`로 확인한다. 다른 Task·이전 revision·중복 보고는 현재 결과를 바꾸지 않는다. 결과에는 실제 수행 내용, 결과물, 실행한 검증, 남은 문제가 포함돼야 한다. 미실행 검증을 통과했다고 표시하지 않는다. 보고 전에 프로세스가 종료되거나 모델이 실패하면 호스트가 실패·중단으로 기록한다. 보고 없는 정상 프로세스 종료도 성공 완료로 간주하지 않는다.

worker가 결과를 보고한 시점과 프로세스·하위 작업이 정리된 시점을 구분한다. 종료 근거 없이 자원이 해제됐다고 기록하지 않는다. 백그라운드 작업이 남아 있으면 정상 응답 종료만으로 메인이나 worker를 회수하지 않는다.

### 6.2 중단 범위를 구분한다

| 사용자 행동 | 효과 |
| --- | --- |
| PTT로 현재 응답 끊기, 응답만 중단 | 메인 응답·음성 출력을 중단한다. 독립 실행 중인 Task 전체를 자동으로 죽이지 않는다. |
| 특정 Task 중지 | 새 실행과 후속 모델 호출을 막고 해당 worker·하위 작업을 정리한다. |
| 전체 작업 중지 | 명시적으로 선택한 범위의 Task를 모두 정리한다. |
| 위임 질문 닫기 | 실행 중지 명령이 아니라 결정의 `pending` 유지다. |

원본 `abort`는 모델 실행만 중단하며 worker와 `bash_async` 작업은 살아 있다. 이 동작을 Picky의 Task 중지로 그대로 노출하지 않는다. 취소 중에는 새 작업 생성과 완료 알림의 재실행을 막고, 정리 확인 후 취소를 확정한다. 종료 여부를 확인할 수 없으면 불확실한 상태를 표시한다.

사용자 중지는 이미 바뀐 파일이나 이미 완료된 외부 효과를 되돌린다는 약속이 아니다. 재개나 인계는 기존 변경과 실행 결과를 먼저 확인한다.

### 6.3 완료는 원요청에 한 번 전달한다

원본은 부모 컨텍스트에 보고가 포함될 때 전달 완료로 표시한다. Picky에서는 저장·모델 소비·사용자 응답 사이의 실패도 다뤄야 한다. 기존 완료 ticket을 연결해 수신·처리·전달 상태를 추적한다.

사용자가 다른 대화를 하는 중이라면 그 응답이나 질문을 끊고 결과를 섞지 않는다. Task 결과는 원요청에 귀속하고 적절한 응답 경계에서 전달한다. 음성 입력 중 완료, PTT 중단 직후 완료, 질문 대기 중 완료도 같은 원칙을 따른다. 결과 처리 도중 실패한 저장만 다시 시도할 수 있어야 하며, 이미 실행한 업무를 알림 재시도를 이유로 반복하지 않는다.

### 6.4 종료·재시작과 자원 제한

앱·agentd가 종료되면 미완료 Task를 중단 상태로 남긴다. 재시작 후 상태와 결과를 복구하고 사용자에게 명시적인 이어가기 경로를 제공한다. 쓰기 작업을 자동 재실행하지 않는다. 같은 논리 Task에서 저장된 child 세션과 실제 작업 상태를 확인해 재개한다. 결정 `pending`도 보존한다.

Task마다 별도 프로세스를 쓰므로 내재화 자체를 메모리·속도 개선이라고 주장하지 않는다. 동시 실행 수·허용 모델·실행 예산은 Picky가 관리한다. 원본의 기본 동시 4개, 30분 진행 알림을 제품의 확정 기본값이나 실행 제한으로 오해하지 않는다. 원본에는 Task 전체의 시간·턴·비용 상한이 없다. 제품 기본 수치와 예산 도달 시 처리는 구현 전에 정하고, 예산 초과를 자동 Pickle 전환으로 처리하지 않는다.

## 7. Task에서 Pickle로 인계

가벼운 작업으로 시작했다가 프로덕션 수준의 코드 작업으로 범위가 확대되면 Task가 이를 Picky에 보고한다. worker가 직접 Pickle을 만들거나 승인 없는 무거운 실행을 시작하지 않는다. 이미 같은 범위에 대해 사용자가 Task 진행을 선택했다면 그대로 수행한다.

첫 버전의 인계는 실행 세션 자체의 변환이 아니다. 새 Pickle을 만들고 기존 작업의 결과·맥락을 전달한다.

1. 현재 Task의 결과와 변경·실행 중인 작업을 기록한다.
2. 추가 실행을 보류하고 Picky가 위임 질문을 표시한다. 폼을 닫으면 보류 상태와 결정 `pending`을 유지한다.
3. 거절하면 같은 논리 Task를 이어간다.
4. 동의하면 기존 Task의 worker·하위 작업 정리를 확인한다.
5. 원요청, 목표·범위, cwd/workspace, 필요한 첨부, 변경 파일, 수행한 검증, 남은 일을 새 Pickle에 전달한다.
6. Task와 Pickle의 연결을 기록한다. Task 자체의 성공 완료와 “Pickle로 전달됨”을 구분한다.

중복 응답·재접속에도 Pickle 생성은 한 번이다. 생성·인계에 실패하면 실행 상태를 숨기거나 Task를 성공 완료로 바꾸지 않는다. 이미 생성된 대상이 있는지 확인하고 같은 인계 작업을 회복한다.

현재 최신 메인 요청을 인계 맥락으로 대신 쓰지 않는다. 다른 대화가 끼어도 원래 Task의 스냅샷과 범위를 전달한다. 인계 후 도착한 옛 Task 이벤트가 대상 Pickle의 상태를 바꾸거나 Task를 다시 실행하지 못하게 한다.

## 8. worker 구성과 컨텍스트

worker는 Picky 번들의 Node·Pi와 Picky가 관리하는 모델·인증·도구·설정을 사용한다. 사용자 Pi 설치나 확장이 없어도 동작해야 한다. 부모의 환경 변수를 무조건 복제하지 않고 필요한 실행 환경을 명시한다. 로그인과 허용 모델이 worker에서도 일치하는지 번들 환경에서 검증한다.

- Task별 실제 작업 폴더를 지정한다. 메인 Picky의 홈을 모든 작업의 cwd로 쓰지 않는다.
- 메인용 라우팅 지침과 worker용 실행 지침을 분리한다. worker가 다시 Picky 역할을 맡아 일을 재위임하지 않는다.
- Task·subagent 재귀 위임은 막는다. Picky 제어 API에서도 worker의 Pickle 생성 경로를 제한하고, `--from-main`을 빼거나 외부 생성 경로를 이용하는 우회 호출을 검토한다.
- 도구 역할 제한과 `readonly`를 OS 샌드박스라고 설명하지 않는다. 공유 파일시스템·자격증명 접근의 실제 경계를 따로 다룬다.
- 같은 파일을 동시에 쓰지 않도록 작업 범위를 분리한다. 충돌 가능성이 있는 작업은 직렬화하거나 명시적인 workspace/worktree 분리를 사용한다.

원요청 snapshot은 후속 메시지와 분리한다. 필요한 업데이트는 Task 수정 지시로 전달하고 revision을 바꾼다. 원본 snapshot은 텍스트 중심이므로 화면·파일 첨부는 별도 전달 계약이 필요하다. 자동으로 부모 대화 전체·다른 Task·현재 화면을 공유하지 않는다. 비밀값 가림은 보조 수단이며 완전한 제외를 보장하지 않는다.

현재 RPC worker는 unattended 입력·승인 dialog를 취소하고 오류로 처리한다. 첫 이관에서는 worker가 필요한 결정과 근거를 구조화해 Picky에 보고하고, Picky가 질문한 뒤 해당 Task에 답을 전달·재개하는 경로를 마련한다. 승인 없이 기본값을 고르거나 질문을 로그에만 남기지 않는다.

Task의 `fast / balanced / powerful`은 실행 모델 선택이다. 직접 응답·Task·Pickle의 제품 라우팅과 합치지 않는다. 높은 tier를 선택했다는 이유로 Pickle을 만들지 않으며, 허용 모델이 없다고 몰래 더 비싼 모델로 전환하지 않는다.

## 9. 화면·음성·원격 사용

Task는 메인 대화 안에서 작업명·현재 상태를 간결하게 표시한다. 상세를 열어 지시, 도구 기록, 결과물, 실제 검증, 실패 원인, 중지·이어가기에 접근할 수 있어야 한다. 완료 시 짧은 요약과 상세 결과를 연결한다. 원본 모델 tier와 내부 로그를 기본 화면에 반복 노출하지 않는다.

현재 응답의 활동 칩과 백그라운드 Task 상태를 분리한다. Picky가 말을 마치거나 칩이 사라져도 실행 중인 Task는 남는다. `pending`, 실행 순서 대기, 실행 중, 사용자 입력 대기, 실패, 취소, 재개 필요를 혼동하지 않게 표시한다. 같은 상태를 여러 배너·행에 중복 표시하지 않는다.

위임 질문은 기존 질문 UI를 재사용하고 음성 답변도 연결한다. PTT를 누르는 순간 질문을 일반 barge-in 취소로 처리해 잃지 않도록 입력 대상을 구분한다. “응”, “아니”처럼 짧은 답은 활성 결정이 명확할 때만 적용하고, 닫힌 질문이나 여러 대기 결정에 임의로 배정하지 않는다. 여러 Task 중 “그거 중지해”의 대상이 불명확하면 확인한다.

긴 결과를 TTS로 전부 읽지 않는다. 요약은 말하고, 긴 보고서·변경 파일·명령 결과는 화면에서 확인한다. 작업이 끝났다고 사용자가 선택한 대화를 자동으로 바꾸지 않는다.

PWA에서도 메인 Task의 상태·질문·중지·결과를 확인하는 최소 경로를 제공한다. 현재 메인 room의 `backgroundTasks: 0` 고정값을 실제 상태로 연결한다. 원격 입력은 Mac 화면 캡처, 선택 대화 변경, 커서 응답, 음성 재생, 권한 프롬프트를 암묵적으로 일으키지 않는다. 사용자가 요청한 파일 열기 등 데스크톱 효과도 입력 출처와 허용 범위에 맞춰 처리한다.

## 10. 적용 범위와 변경 위치

### 10.1 첫 구현에 포함한다

- 메인 Picky의 음성·빠른 입력·텍스트·원격 요청에 동일한 네 단계 정책 적용.
- Picky 전용 Task 소스 이관, 번들 worker 실행, 모델·설정·인증 연결.
- 위임 결정과 `pending` 영속화, 거절 후 Task 실행, 명시적 위임의 즉시 실행.
- Task 상태·상세·결과·질문·중단·수정 지시·명시적 재개.
- 메인 작업 추적과 완료 전달, PTT·다른 요청·컴팩션·재접속과의 경합 처리.
- Task에서 Pickle로의 인계와 중복 실행 방지.
- 기존 정책 마이그레이션과 관련 문서·Skill·행동 테스트 갱신.

### 10.2 함께 바꾸지 않는다

- 기존 Pickle 대화의 직접 입력·후속 지시·내부 subagent 실행 방식.
- 기존 Pickle을 일괄 Task로 바꾸거나 대화 기록을 병합하는 작업.
- 독립 Task daemon, 앱 종료 후 무중단 실행, 무조건 자동 재시작.
- Task의 재귀 위임과 자동 작업 분해, 자동 모델 승격.
- RPC worker를 SDK worker로 전면 재작성하는 작업.
- 기획서 B 전체 메신저·봇·Routine·컴퓨터 제어 개편.
- Task 이관을 빌미로 사용자 전역 Pi 데이터나 다른 익스텐션을 삭제하는 작업.

### 10.3 구현 진입점

새 파일의 정확한 이름은 구현 단계에서 정한다. 기존 경계와 책임을 우선 재사용하고 아래 큰 파일에 모든 Task 로직을 덧붙이지 않는다.

| 질문·피클 생성 | [ask tool](../agentd/src/runtime/ask-user-question-tool.ts), [UI bridge](../agentd/src/runtime/extension-ui-bridge.ts), [server](../agentd/src/server.ts), [CLI](../agentd/src/cli.ts) | 닫기를 승인으로 보지 않는 경로, 원요청·범위 연결, 생성 중복·우회 방지. |
| Mac 표시·입력 | [메인 대화](../Picky/MainAgent/PickyMainAgentConversationStore.swift), [메인 활동](../Picky/MainAgent/PickyMainAgentActivityStore.swift), [background presentation](../Picky/HUD/Conversation/PickyBackgroundWorkFooterPresentation.swift), [음성 대상 정책](../Picky/Companion/PickyVoiceTranscriptRoutingPolicy.swift) | 메인 Task 표시와 제어, 응답/작업 수명 분리, 질문 음성 답변. |
| 원격 | [gateway rooms](../agentd/src/gateway/rooms.ts), [PWA](../agentd/web/), [main adapter](../Picky/Remote/PickyRemoteMainAgentAdapter.swift) | 메인 작업 상태·질문·제어, remote origin 보존. |
| 패키징 | [runtime package](../scripts/package-agentd-runtime.sh), [provider install](../scripts/install-async-task-providers.mjs) | 내재화한 소스와 worker bridge 포함, 외부 Task npm 설치 의존 없음. |
| 안내 | [Picky CLI skill](../pi-skills/picky-cli/SKILL.md), [사용자 매뉴얼](./user-manual.md) | 기존 자동 위임 설명을 새 정책과 일치시킴. |

상시 라우팅 정책은 매 턴 주입되는 Picky 런타임 계약에 둔다. seed와 bootstrap에 독립된 판단 기준을 중복하지 않는다. 변하는 Task 상태와 질문 데이터는 요청 맥락으로 전달하고, 시스템 정책 문자열에 매번 섞지 않는다.

사용자가 수정한 `AGENTS.md`는 덮어쓰지 않는다. 알려진 자동 생성본만 식별해 마이그레이션하며, 과거 기본값 식별 문자열을 일괄 치환하지 않는다. 옛 대화·메모리·Skill에 남은 자동 위임 규칙이 새 정책을 되살리지 않도록 로딩 범위와 우선순위를 정리한다. 사용자 전역 파일은 이 작업에서 수정하지 않는다.

wire 계약을 바꾸면 TypeScript·Swift·fixture를 함께 갱신한다. `PickyAgentSession` 필드를 추가하는 경우 기존 session-field 단일 테이블과 생성 경로를 사용한다. 메인 상태에 필드를 추가하는 일과 Pickle metaPatch 필드 추가를 혼동하지 않는다.

## 11. 이관 순서와 검증 기준

### 11.1 이관 순서

1. 원본 코드·테스트·라이선스를 보존하고 내장 Task 모듈을 만든다. 큐·revision·보고·같은 RPC worker 재개 계약을 먼저 확보한다.
2. Picky 저장·async host·완료 ticket·worker 종료·격리된 번들 환경을 연결한다. 메인 작업 UI와 제어도 함께 검증한다.
3. 위임 결정·`pending`·음성 답변·거절 후 Task·Task에서 Pickle로의 인계를 연결한다.
4. 상시 라우팅 정책과 기존 설치 마이그레이션을 적용하고 아래 전체 경로를 검증한다.

Task 추적·제어가 없는 상태에서 정책부터 바꾸어 출시하지 않는다. 단계는 구현 순서이며 별도의 제품 모드나 사용자용 옵트아웃을 요구하지 않는다.

### 11.2 검증할 관찰 가능한 결과

아래는 구현 합격 기준이며 현재 통과했다는 기록이 아니다.

| 시나리오 | 기대 결과 | 검증 경계 |
| --- | --- | --- |
| 번역, 파일 탐색, 일회성 스크립트, 제품 버그 수정, 명시적 위임 | 각각 직접·Task·Task·질문·즉시 Pickle 경로. 긴 조사만으로 질문하지 않음. | 대표 요청의 모델 분류 평가 + 실제 실행 경로 통합 |
| 무거운 요청의 답변 전·거절·폼 닫기 | 답변 전 미실행, 거절 후 Task, 닫기 후 영속 `pending`. | 실제 질문 응답 → 결정 저장 → worker/생성 경계 |
| 중복 답변·옛 폼 답변·재접속 | 생성 한 번, 옛 범위 실행 없음, pending 복구. | daemon·저장·클라이언트 계약 |
| 같은 범위를 Task로 선택한 뒤 코드 수정·빌드 | 다시 위임 질문하지 않고 선택한 Task에서 수행. | 정책 + Task 후속 실행 |
| 진행 중 수정과 늦은 이전 보고 | 새 revision의 최종 결과만 현재 작업에 반영. | 이관 engine/RPC 테스트 |
| 다른 대화·음성 입력·질문 대기 중 Task 완료 | 원요청에 귀속되고 중복 없이 전달. 현재 입력·질문을 잃지 않음. | production 이벤트 → 영속 상태 → Swift/PWA projection |
| 응답 중단과 Task 중지 | 응답만 중단하면 Task 유지. Task 중지는 하위 작업 정리와 재실행 차단까지 확인. | 실제 worker·비동기 작업 수명 통합 |
| 컴팩션·메인 세션 교체·앱 재시작 | Task와 결정 접근 유지, 미완료는 명시적 재개, 자동 쓰기 재실행 없음. | 저장·복구·runtime 교체 |
| Task에서 Pickle 인계와 생성 실패 | 기존 변경 보존, 중복 worker 쓰기·Pickle 생성 없음, 인계 실패를 성공으로 숨기지 않음. | Task 종료 → 기존 생성 경로 → 저장된 최종 결과 |
| 화면 첨부·다른 cwd·원격 요청 | 원요청의 허용된 맥락 전달, 작업 폴더 일치, 원격의 암묵적 Mac 효과 없음. | prompt/첨부·런타임·remote 연동 |
| 사용자 Pi가 없는 번들 실행 | 번들 Node·Pi·도구로 worker 생성·작업·보고·정리 가능. | 격리된 packaged runtime smoke |
| 기존 사용자 수정 seed·옛 기본값·옛 세션 | 사용자 파일 보존, 자동 생성본만 이전, 새 라우팅 적용. | 마이그레이션·실제 prompt 경로 |

모델의 자연어 분류는 대표 사례로 평가하고, 승인·취소·중복 방지·저장은 결정적인 통합 테스트로 검증한다. 프롬프트에 특정 문장이 있는지만 검사해 라우팅이 보장됐다고 주장하지 않는다. 기존 Task offline PoC는 이관 출발점이며 Picky 앱 연동의 증거를 대신하지 않는다.

바뀐 계약의 가장 좁은 테스트와 Swift/TypeScript 호환 검사를 먼저 수행한다. 문서 작성 단계에서는 제품 테스트나 앱 빌드를 실행하지 않는다. 구현 검증도 실행 중인 사용자 앱 재시작 없이 격리된 runtime·임시 저장소를 사용한다. 실제 음성·화면 검증은 실행한 범위와 한계를 따로 기록한다.

## 12. 구현 전에 정할 세부값

다음은 확정 정책을 다시 논의할 항목이 아니라 구현에 필요한 세부값이다. 미정 값을 이미 승인된 수치처럼 하드코딩하지 않는다.

| 항목 | 정할 내용 |
| --- | --- |
| 자원·실행 예산 | 기본·최대 동시 실행 수, 시간·턴·사용량 상한, 한도 도달 시 중단·회복 동작. |
| 모델 설정 | 사용 가능한 계정별 evaluator와 tier preset, 허용 범위, 인증 실패 안내. |
| 보존·정리 | 완료 Task 기록·child 대화·컨텍스트의 보존 기간과 삭제 범위. 사용자 작업 파일 삭제와 구분. |
| 화면 세부 | 메인 Task 표시 위치·상세 구성·음성 질문 처리의 구체 상호작용. 상태·제어·접근성 계약은 유지. |
| 데이터 모델 | 기존 async 계약을 재사용할 필드, 결정·인계 저장 위치, 이전 payload 호환 방식. |
| 독립 패키지 종료 | 이관 후 원본 보존 위치와 npm deprecate/unpublish 여부·시점. |
