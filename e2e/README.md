# Picky E2E 시나리오 매뉴얼

Picky가 사용자에게 보장해야 할 행동을 여정별로 정리하고, 그 약속을 검증하는 테스트와 연결한다. 화면이나 버튼 목록보다 사용자의 목적, 실패했을 때의 영향, 복구 방법을 먼저 기록한다.

현재는 시나리오를 정리하는 단계다. 이 폴더에 E2E 실행기나 새 자동화 테스트는 아직 없다. 문서·구현·기존 테스트를 읽은 사실을 실제 앱에서 검증한 결과로 취급하지 않는다.

## 첫 여정

| 여정 | 범위 | 진행 상태 |
| --- | --- | --- |
| [INPUT: 입력 대상을 지정하고 요청을 전달한다](scenarios/input-routing.md) | Mac의 대상 지정, PTT, Quick Input, 전달·취소·재시도 | 정상 사용법과 시나리오 초안, 기존 테스트 근거, 미결정 항목 정리 |

여정별 문서는 `scenarios/`에 둔다. 네이티브·데몬 테스트를 이 폴더로 옮기거나, 문서를 실행하는 별도 언어를 만드는 일은 지금 범위에 포함하지 않는다.

## 시나리오를 도출하는 순서

### 1. 사용자 목표로 기능을 묶는다

예를 들어 "Dock 테스트" 대신 "특정 작업에 추가 지시를 전달한다"를 여정으로 잡는다. 음성, Quick Input, 대화창은 그 목적을 달성하는 진입점이다. 목적과 기대 결과가 같으면 진입점마다 문서를 복제하지 않는다. 대상 결정 시점이나 취소 범위가 다르면 별도 시나리오로 구분한다.

시작 자료는 [사용자 매뉴얼](../docs/user-manual.md)의 Common workflows다. 이 목록이 제품 전체를 빠짐없이 설명한다고 가정하지 않는다.

### 2. 여러 근거를 대조한다

| 근거 | 추출할 내용 | 한계 |
| --- | --- | --- |
| 매뉴얼·가이드·제품 결정 | 의도한 사용법과 결과 | 구현보다 오래됐을 수 있다. |
| UI·단축키·CLI·프로토콜 | 가능한 행동과 실제 진입점 | 기능 목록만으로 사용자 목적을 알 수는 없다. |
| 라우팅·상태 전이·저장 코드 | 대상 선택, 중간 상태, 취소와 복구 | 현재 구현에 있는 버그까지 정답으로 굳히지 않는다. |
| 기존 테스트·버그·사용자 피드백 | 명시된 계약과 반복해서 깨진 조건 | 기존 테스트가 없는 영역도 조사한다. |

후보에는 근거 파일과 관련 심볼을 붙인다. AI로 추출할 때도 확인되지 않은 기대 동작을 표시하게 한다. 코드에서 발견한 행동과 제품이 보장하기로 한 행동은 구분한다.

### 3. 진입점부터 사용자가 확인하는 결과까지 추적한다

`사용자 행동 → 대상 결정 → 명령 전달 → 상태·저장 변경 → 화면 표시`를 확인한다. 입력을 보냈다는 콜백이나 패널이 닫혔다는 사실만으로 전달 성공을 판정하지 않는다.

각 경계에서 취소, 연속 입력, 대상 변경, 지연, 중복 이벤트, 연결 끊김, 재진입을 검토한다. 모든 조합을 만들기보다 잘못된 대상에 전달, 데이터 유실, 중복 실행, 복구 불가부터 우선한다.

### 4. 기대 결과와 미결정 사항을 분리한다

문서와 코드가 다르거나 실패 후 행동이 불명확하면 양쪽 근거와 필요한 결정을 남긴다. 테스트를 작성하면서 임의로 제품 정책을 정하지 않는다. 미결정 사항과 무관한 정상 흐름은 계속 정리한다.

### 5. 가장 작은 검증 경계를 연결한다

기존 테스트를 먼저 찾고, 실제로 보장하는 부분과 남은 부분을 기록한다. 순수 정책·앱 orchestration·데몬 통합 테스트를 UI E2E로 다시 구현하지 않는다. 실제 클릭, 키 입력, 포커스, 창 전환이 필요한 연결점에 UI 검증을 추가한다.

E2E에서는 제품의 라우팅·저장·프로토콜 경로를 실제로 통과시킨다. LLM, STT/TTS 같은 외부 경계는 결정적인 대역을 쓸 수 있지만, 화면 상태를 직접 바꾼 것을 요청 전달 검증으로 세지 않는다. 자세한 기준은 [테스트 작성 지침](../.agents/skills/test-writing-guidelines/SKILL.md)을 따른다.

## 시나리오 기록 형식

```text
ID: INPUT-001
사용자 목적:
조건: 시작 상태, 입력 경로, 필요한 설정
행동: 사용자가 하는 일과 주입할 장애 또는 동시 행동
기대 결과: 화면과 최종 저장 상태에서 확인할 결과, 일어나면 안 되는 일
우선순위: P0 / P1 / P2
계약 상태: 근거 일치 / 구현 관찰 / 결정 필요 / 폐기
근거: 사용자 문서·제품 결정, 구현 파일과 심볼
검증 연결: 기존 테스트가 보장하는 범위, 부족한 범위
```

- P0는 오전송, 유실, 중복 실행, 취소 무시처럼 신뢰를 깨는 계약이다.
- P1은 주요 정상 흐름과 복구·표시 계약이다.
- P2는 낮은 빈도의 주변 조건이다. 드물어도 피해가 크면 P0로 올린다.
- 공통 조건과 검증 한계는 여정 문서 앞부분에 모으고, 각 시나리오에는 차이만 쓴다.
- 클릭 좌표, private 메서드 순서, SwiftUI 내부 구조는 기대 결과로 쓰지 않는다. 구현 심볼은 탐색용 근거다.

## 계약 상태와 실행 결과를 구분한다

| 계약 상태 | 의미 |
| --- | --- |
| 근거 일치 | 기존 사용자 문서 또는 명시된 제품 결정과 구현이 일치한다. 테스트 통과를 뜻하지 않는다. |
| 구현 관찰 | 코드와 기존 테스트에서 현재 행동을 찾았지만, 사용자에게 보장할 범위를 추가로 확인해야 한다. |
| 결정 필요 | 기대 동작이 비어 있거나 근거 사이에 차이가 있어 제품 결정이 필요하다. |
| 폐기 | 기능이 사라지거나 다른 계약으로 대체됐다. 대체 ID나 제거 이유를 남긴다. |

검증 연결에는 `미자동화`, `부분 검증`, `E2E 연결`을 구분한다. 테스트 파일이 있다는 이유만으로 E2E 연결이나 통과로 표시하지 않는다. 실행 결과에는 해당 리비전, 환경, 실제 실행한 케이스, 결과와 산출물을 남긴다. 건너뜀, 0건 실행, 권한·환경 때문에 실행하지 못한 상태는 통과가 아니다.

현재 문서의 기존 테스트 링크는 소스 조사 근거다. 이번 문서화 과정에서는 제품 테스트를 실행하지 않았다.

## 시각·애니메이션 조건을 붙이는 방법

시나리오의 의미 있는 상태와 전환에 시각 조건을 붙인다. 예를 들어 수신자 표시, 전송 중 숨김, 실패 후 입력창 복원은 같은 전달 여정의 관찰 지점이다.

- 정적 장면은 긴 이름, 좁은 폭, light/dark 등 실제 위험이 있는 변형만 선택한다.
- 애니메이션은 시작·끝 이미지뿐 아니라 중간의 잘림, 깜빡임, 위치 점프와 전환 취소를 별도로 정의한다.
- 시간·이름·배율·appearance 등 비교 조건을 고정하고, 기준 이미지 변경은 사람이 검토한다.
- 모든 기능 시나리오와 모든 화면 조건의 곱을 만들지 않는다. 관련 없는 축은 대표 조합으로 줄인다.
- 기존 [렌더 갤러리](../docs/render-gallery.md)의 해상도·material·상호작용 한계를 명시한다. 정적 PNG를 애니메이션이나 실제 키 입력의 증거로 쓰지 않는다.

## 유지보수 규칙

1. 사용자에게 보이는 행동을 바꾸는 변경에서 해당 시나리오도 갱신한다. 동작을 보존하는 리팩터링은 기대 결과를 바꾸지 않는다.
2. 버그를 고칠 때 기존 계약의 누락인지 검증의 누락인지 먼저 구분한다. 이미 적힌 계약이면 같은 ID에 회귀 근거를 연결한다.
3. ID는 순서를 바꿔도 유지하고 재사용하지 않는다. 폐기된 시나리오는 활성 목록에서 제외하되 이유와 대체 관계를 남긴다.
4. 조작 방법의 정본은 사용자 매뉴얼, 실패·경합의 기대 결과와 검증 연결은 이 폴더에 둔다. 같은 정책을 여러 문서에 길게 복제하지 않는다. 서로 다른 내용은 미결정 항목으로 드러낸다.
5. 테스트를 추가할 때 시나리오 ID를 테스트 이름이나 설명에 연결한다. 앞으로 검증 현황은 이 연결과 실제 실행 보고서에서 만들고, 별도의 수동 통과표를 중복 관리하지 않는다.
6. 기능 제거·라우팅 변경 때 관련 근거 링크와 시나리오를 함께 검토한다. 기준 이미지나 assertion을 바꿔 실패만 없애지 않는다.

## 실행 경계와 다음 단계

실제 데스크톱 조작은 [테스트 데스크톱 격리 규칙](../docs/test-desktop-isolation.md)을 따른다. 실행 중인 사용자 Picky를 재시작하거나, 실제 홈·세션·권한을 테스트 준비에 사용하지 않는다. 문서만 바꿀 때는 저장 내용, 링크와 diff를 확인하고 앱 빌드나 제품 테스트를 돌리지 않는다.

먼저 INPUT 여정의 기대 결과와 미결정 항목을 검토한다. 그다음 정상 전달 하나와 지연·취소 하나를 격리된 환경에서 실제 입력부터 최종 화면·저장까지 연결한다. 이때 사용한 기록 방식과 검증 경계가 적절한지 확인한 뒤 다른 여정으로 넓힌다.
